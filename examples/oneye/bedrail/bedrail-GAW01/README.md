# bedrail-GAW01 · 床护栏网关（ESP32-S3-Zero / ESP32-C3-Zero）

> 本工程由 `bedrail/gateway`（ESP32-C6-GEEK 版）**原样复制**而来：入网（BLE 配网 + Wi-Fi + 云端 TLS/MQTT）、
> 子设备配对、`sub.*` 上报、creds 分区凭据等实现**全部复用**；差异只在「目标芯片 / 分区表 / 板级外设」。
> 原 gateway 的详细行为（角色、`gw_child` 的 `cmd=0x03` 单帧上报、节流口径）仍见 git 历史中的那份 README。

## 1. 支持的目标

| 目标 | 板子 | Flash | 分区表 | 实测 |
| --- | --- | --- | --- | --- |
| `esp32s3` | ESP32-S3-Zero（COM9，MAC `a0:f2:62:ea:6a:ec`） | 4 MB | `partitions-4mb.csv` | ✅ 构建 + 烧录 + 启动（2026-11-18） |
| `esp32c3` | ESP32-C3-Zero | 4 MB | `partitions-4mb.csv` | ✅ 构建（`bedrail_gateway_c3.bin` 1.51 MB），无 C3 硬件未烧 |

> ⚠️ `COM4` 上那块经 esptool 实测是 **ESP32-C6FH8 / 8 MB**，不是 C3；C3 产物不要烧到 COM4。

## 2. 构建

```powershell
. E:\esp\esp-idf-5.5.5\export.ps1
cd embedded\esp-adf\examples\oneye\bedrail\bedrail-GAW01

idf.py set-target esp32s3     # 或 esp32c3
idf.py build
idf.py -p COM9 -b 460800 flash monitor
```

`CMakeLists.txt` 按 `IDF_TARGET` 自动叠加 `sdkconfig.defaults.<target>(.mem)`，无需手写 `-D`。

实测产物（S3）：`bedrail_GAW01.bin` **1,396,368 B**（0x154e90），factory 分区 3 MB 余量 **55%**。

## 3. 分区表（`partitions-4mb.csv`）

```text
nvs      0x9000   24 KB
phy_init 0xf000   4 KB
factory  0x10000  3 MB      ← app
creds    0x300000 16 KB     ← 一机一密凭据（⚠️ 不是 korvo2/C6 的 0x510000）
```

SDK 按 `(type, subtype, name)` 找分区，偏移对固件无感；但**产测/凭据烧写脚本按偏移直写时必须以本表为准**。

## 4. 与签发服务（`backend/deployment/signer`）的衔接

`deploy/s3-zero-a0f262ea6aec.csv` 是**云端批量录入**模板（列名逐字对齐 `ProvisionTemplateCsv` 的别名），
`证书序列号` / `设备公钥` 两列由 signer 回执回填：

```http
POST /v1/sign      {"node_id":"GAW01-A0F262EA6AEC","validity_days":3650}   → 证书 + 私钥
POST /v1/sign-pub  {"node_id":"…","public_key_pem":"…"}                    → 只回证书
```

详见 `deploy/README.md`。

## 5. 当前状态与下一步

- ✅ 入网与子设备实现直接复用；S3 上已启动运行（日志 `t31gw` / `boardkey` 正常，Wi-Fi 处于 AP/配网态）；
- ⏳ **床护栏传感器的广播接收**：传感器是纯广播（厂商数据 `0x4F59` + v5 TLV），现有 `gw_child.c`
  走的是 T31「连接后读 TLV」路径 ⇒ 待新增 `gw_adv.c`：

  `sub.telemetry {node:<MAC>, model, rssi, cmd:3, tlv:<hex>}` → 复用 `gw_child` 的 `emit_event` 出口；
- ⏳ 凭据：本板暂无 creds，先验证「收广播 + 解析 TLV」，云端上报等凭据就绪。
